# レビューの観点

公開前に、記事の本文と、記事が使っている画像（`images/<slug>/`）をすべて確かめる。画像は Read で開いて、実際に何が写っているかを見る。

記事は public な GitHub と Zenn の両方に出る。一度公開すると、消してもどこかに残る可能性があるので、ここで止めることがいちばん大事。

## 観点

| 観点 | 確かめること | なぜ |
|---|---|---|
| 個人情報（本文） | aki の本名、普段使いのメールアドレス、塗りつぶされていないアカウント ID・ARN・IP アドレス・アクセスキー・ユーザー名・組織 ID・アクセスポータルの URL など。Windows のユーザーフォルダのパス（`C:\Users\...`）にも本名が含まれる | aki は技術系の活動では本名を出さない名義（aki / akino）を使っている。AWS の識別子は攻撃の手がかりになる |
| 個人情報（画像） | 上と同じものが写っていないか。AWS コンソールのヘッダー（アカウント名・メールアドレス）が写っていないか | 画像の中の文字は、文章のチェックでは見つからない |
| 誤字脱字・文章 | 誤字、脱字、変換ミス、意味の通らない文、表記の揺れ | 読みにくい記事は、内容が正しくても読まれない |
| 書き方 | 個人の学習記録として書かれているか。会社や業務を前提にした表現（「会社の検証環境」「業務では」など）がないか | aki の記事は会社のブログではなく、個人の学習記録 |
| 事実の食い違い | AI の解説と ✍️ 欄の内容が食い違っていないか。食い違っていたら、What's New やドキュメントでどちらが正しいかを確かめて指摘する | 実際に試した結果のほうが正しいことが多く、AI の解説を直すきっかけになる |
| タイトル | AWS のアップデートのタイトル（What's New の見出し）をそのまま、または言い換えただけになっていないか。✍️ 欄で aki が実際にやったこと（試した・調べた・比べた など）が伝わるか | 同じアップデートの記事はたくさん出るので、「この人は何をしたのか」がタイトルでわかると読んでもらえる |

IP アドレスのうち、文書用の例示アドレス（192.0.2.0/24・198.51.100.0/24・203.0.113.0/24）は問題ない。

## 本名とメールアドレスの扱い

本名や普段使いのメールアドレスを見つけたら、「どこにあったか」だけを伝える。チャット・ファイル・PR の本文には書き写さない。書き写すと、それ自体が新しい漏れ道になるため。

## 指摘があったとき

- 指摘と直し方の案を aki に見せ、aki が OK した直しだけを記事に反映する。✍️ 欄は aki の文章なので、頼まれずに書き換えない
- タイトルが観点に合っていなければ、✍️ 欄の内容に合わせた案を 2〜3 個出して、aki に選んでもらう（例:「AWS Client VPN の新機能「デバイスポスチャ評価」を試してみた」）。aki が自分で考えたタイトルにしてもよい
- 個人情報が写った画像は、Claude には加工できない。aki に差し替えを頼み、差し替わるまで PR を作らない
