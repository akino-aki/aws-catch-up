# aws-weekly

週刊AWS の新しい号に載ったアップデートを、1 件ずつ Zenn 記事の下書きにする。

aki はこの下書きの「✍️ 自分の調査・勉強結果」を自分で書き、書き終えたものから公開していく。このスキルの役目は、その出発点になる下書きを、サービスを知らない人でも読めるわかりやすさで用意しておくこと。公開はしない（公開は aki が頼んだときに `/aws-publish` で行う）。

運用の全体像は `docs/workflow.md`、記事の書き方のルールは `CLAUDE.md` にある。先に読んでおくと、下書きの粒度を合わせやすい。

## 全体の流れ

```
0. 準備        work ブランチを最新にする
1. 確認        最新号がもう収集済みなら、何もせず終わる
2. 収集        アップデートごとに What's New を読み、下書きを drafts/<週>/ に書く
3. 確かめる    スクリプトで形をチェックする
4. 記録・push  collected-weeks.txt に週を記録し、コミットして push する
5. 報告        何が起きたかを短くまとめる
```

## 引数（モード）

`$ARGUMENTS` からモードを決める。

| 引数 | モード | やること |
|---|---|---|
| なし | 通常（ルーティン） | 最新号がまだ収集されていなければ収集する |
| `YYYY-MM-DD` | 週の指定 | その週を収集する（さかのぼり収集など）。手順 1 は飛ばす |
| `--dry-run` を含む | お試し | 上のどちらかを、記録・コミット・push をせずに行う |

週は「対象週の月曜日」の日付で表す。`週刊AWS – 2026/9/28週` なら `2026-09-28`。

`--dry-run` は動作確認のためのモード。GitHub にも aki の作業にも影響を残さないことが目的なので、下書きのファイルは中身を確認できるように作ってよいが、`collected-weeks.txt` の更新・コミット・push はしない。

## 0. 準備

```bash
git fetch origin
git switch work
git pull --ff-only
```

`work` に未コミットの変更があれば、触らずに報告して終わる。aki が書きかけている内容かもしれず、混ぜてコミットすると aki の作業を壊してしまうため。

`npm install` / `npm ci` は不要。`scripts/` のスクリプトは Node.js の標準機能だけで動く（`zenn-cli` はプレビュー用で、この作業では使わない）。クラウドの環境ではパッケージの取得先への通信が許可されていないので、実行すると時間を無駄にする。

## 1. 確認（通常モードのみ）

```bash
node scripts/fetch-weekly.js latest
```

出力の `week` が `collected-weeks.txt` にあれば、新しい号はまだ出ていない。何もせず「新しい号なし」と報告して終わる。なければ 2 に進む。

週刊AWS は祝日の週に遅れたり、お休みの週があったりする。出ていない日に何もしないのは正しい動きなので、失敗として扱わない。

週の指定モードで、指定した週がすでに `collected-weeks.txt` にあるときは、作り直してよいか判断できないので、報告して終わる。

## 2. 収集

### 材料を集める

```bash
node scripts/fetch-weekly.js week <week>
```

アップデートの一覧（掲載日 `day`・タイトル・What's New の `url`・週刊AWS の説明）が JSON で出てくる。

続けて、アップデートごとに What's New のページ（`url`）を WebFetch で読み、料金・対象リージョン・前提条件などの事実を確かめる。週刊AWS の説明は要約なので、細かい条件が抜けていることがあり、それをそのまま解説に書くと間違いの元になる。件数が多いので、並行して読んでよい。

### 下書きを書く

`templates/article.md` をもとに、`CLAUDE.md` の「下書きの作り方」に従って、1 アップデートにつき 1 本を `drafts/<week>/<slug>.md` に書く。表や注釈をどれくらい使うかは、既存の下書きか記事を 1 本読んでから合わせる。

| 項目 | 決め方 |
|---|---|
| ファイル名（slug） | `aws-YYYYMMDD-<短い英語名>`。日付は What's New の掲載日（`day`。年は対象週から決める。年をまたぐ週は年がずれるので注意）。英小文字・数字・ハイフンだけで、全体で 12〜50 文字（Zenn の制限） |
| タイトル | 頭に What's New の掲載日を `【YYYY/M/D アップデート】` の形で付ける。そのあとは仮のタイトルでよく、アップデートの中身を自分の言葉で表す（例:「【2026/10/6 アップデート】CloudWatch Logs がよく検索するフィールドに自動でインデックスを付けるようになった」）。頭の部分も含めて 70 文字まで。最終的なタイトルは、aki が ✍️ 欄を書いたあと、公開のレビューで決める |
| topics | `"aws"` と、サービス名などを英小文字・数字だけで 1〜3 個（例: `["aws", "cloudwatch"]`） |
| はじめに | 「YYYY/M/D に発表された「What's New の元のタイトル」について、調べたことをまとめます。」の 1 文、What's New の URL だけの行、AI が書いた旨の注意書き（テンプレートのとおり） |
| 参考 | 週刊AWS のその号と、What's New へのリンク |
| published | `false`。公開するかどうかは aki が決めるため |

書くときに気をつけること:

- **既存の下書きや記事を上書きしない。** 同じ slug のものがあれば、そのアップデートは作らない。aki の勉強が書かれているかもしれず、上書きすると取り戻せない
- **「✍️ 自分の調査・勉強結果」には何も書かない。** テンプレートのコメントのまま残す。ここに AI が書くと、aki が書いていない内容が aki の言葉として公開されてしまう（CI でも止まる）
- **週刊AWS の説明文を写さない。** タイトルとリンク以外は自分の言葉で書く。読者はサービスを使ったことがない人を想定する
- **個人の学習記録として書く。** 会社や業務を前提にした書き方をしない

## 3. 確かめる

```bash
npm run check -- --lint
npm run check
```

- `--lint` が NG なら、エラーの内容に従って直す
- `npm run check` の一覧で、作った下書きがすべて `drafts/<week>/` にあり「✍️ なし」になっていることを確かめる

## 4. 記録してコミットし、push する

```bash
echo "<week>" >> collected-weeks.txt
git add drafts/<week>/ collected-weeks.txt
git commit -m "collect: YYYY/M/D週の下書き（N 本）を作成"
node scripts/check-collect.js HEAD~1 HEAD
git push
```

`collected-weeks.txt` に記録するのは、aki が興味のない下書きを消したあとでも、同じ週をもう一度収集しないようにするため。

`--dry-run` では、この手順を行わない。作った下書きは未コミットのまま残し、その旨を報告する。

## 5. 報告

最後に、次の形で短く報告する。ルーティンの実行ログとして aki があとから読むので、何が起きたかがひと目でわかるようにする。

```
## aws-weekly の結果（<モード>）
- 確認: 新しい号あり（2026/10/5週） / 新しい号なし
- 収集: 下書き 15 本を drafts/2026-10-05/ に作成 / スキップ
  - aws-20261005-xxx: タイトル
  - …
- 注意: （あれば。チェックの NG、取得の失敗、作らなかったアップデートなど）
```

## うまくいかないとき

- **`fetch-weekly.js` が失敗する**（ネットワークの制限、ページの構造の変更など）: WebFetch で週刊AWS のページを読んで代わりにしてよい。その場合、What's New のリンクは記事内では相対パス（`/about-aws/...`）なので、`https://aws.amazon.com` を付けた完全な URL にする。構造の変更でスクリプトが壊れていそうなら、報告に書いておく
- **push が権限で失敗する**: 回避しようとせず、何が失敗したかを報告して終わる
- **途中で失敗した**: 中途半端なコミットを push しない。どこまで終わったかを報告する
