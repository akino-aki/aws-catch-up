# aws-weekly

週刊AWS に載ったアップデートごとに、Zenn 記事の下書きを `drafts/<週>/` に作る。
運用の全体像は `docs/workflow.md`、記事の書き方は `CLAUDE.md` にある。このスキルはその手順のうち「収集」を実行するためのもの。

**このスキルでは公開しない。** 公開は aki が「公開して」と言ったときだけ、スキル `/aws-publish` で行う。

## 引数

`$ARGUMENTS` を見て、モードを決める。

| 引数 | モード | やること |
|---|---|---|
| なし | 通常（ルーティン） | 最新号がまだ収集されていなければ収集する |
| `YYYY-MM-DD` | 週の指定 | その週を収集する（さかのぼり収集など） |
| `--dry-run` を含む | お試し | 上のどちらかを、コミット・push をせずに行う |

週は「対象週の月曜日」の日付で表す（`週刊AWS – 2026/9/28週` なら `2026-09-28`）。

`--dry-run` は動作確認のためのモード。下書きのファイルは中身を確認できるように作ってよいが、`collected-weeks.txt` の更新・コミット・push はしない。

## 0. 準備

```bash
git fetch origin
git switch work
git pull --ff-only
```

`work` に未コミットの変更があるときは、aki の作業中のものかもしれないので、触らずに報告して終了する。

`npm install` / `npm ci` は不要。`scripts/` のスクリプトは Node.js の標準機能だけで動く（`zenn-cli` はプレビュー用で、この作業では使わない）。クラウドの環境ではパッケージの取得先への通信が許可されていないこともある。

## 1. 確認（通常モードのみ）

```bash
node scripts/fetch-weekly.js latest
```

出力の `week` が `collected-weeks.txt` にあるか確認する。

- **ある** → 新しい号はまだ出ていない。何もせず「新しい号なし」と報告して終了する
- **ない** → 新しい号が出ている。2 に進む

週刊AWS は祝日の週に遅れたり、お休みの週があったりする。出ていない日は何もしないのが正しい動きなので、失敗扱いにしない。

週の指定モードで、指定した週がすでに `collected-weeks.txt` にあるときは、もう一度作ってよいか分からないので、報告して終了する。

## 2. 収集

### 2-1. 材料を集める

```bash
node scripts/fetch-weekly.js week <week>
```

アップデートの一覧（掲載日・タイトル・What's New の URL・週刊AWS の説明）が JSON で出てくる。

さらに、**アップデートごとに What's New のページ（`url`）を WebFetch で読み**、料金・対象リージョン・前提条件などの事実を確かめる。週刊AWS の説明は要約なので、細かい条件が抜けていることがある。件数が多いときは、並行して読んでよい。

### 2-2. アップデートごとに下書きを書く

`templates/article.md` をもとに、`CLAUDE.md` の「下書きの作り方」に従って、1 アップデート 1 本を `drafts/<week>/<slug>.md` に書く（`<week>` は対象週の月曜日 `YYYY-MM-DD`）。表や注釈の使い方の粒度は、既存の下書きや記事（`drafts/`・`articles/`）を 1 本読んでから合わせる。

| 項目 | 決め方 |
|---|---|
| ファイル名（slug） | `aws-YYYYMMDD-<短い英語名>`。日付は What's New の掲載日（`day`。年は対象週から決める。年をまたぐ週に注意）。英小文字・数字・ハイフンだけで、全体で 12〜50 文字 |
| タイトル | アップデートの中身を自分の言葉で表す（例:「CloudWatch Logs がよく検索するフィールドに自動でインデックスを付けるようになった」）。70 文字まで |
| topics | `"aws"` と、サービス名などを英小文字・数字だけで 1〜3 個（例: `["aws", "cloudwatch"]`） |
| 導入文 | 「YYYY/M/D に発表された「What's New の元のタイトル」について、調べたことをまとめます。」の 1 文と、What's New の URL だけの行 |
| 参考 | 週刊AWS のその号と、What's New へのリンク |

特に間違えやすいところ:

- 同じ slug の下書きや記事がすでにあれば、そのアップデートは作らない。aki の勉強が書かれているかもしれないので、上書きは絶対にしない
- 「✍️ 自分の調査・勉強結果」は aki が書く欄。テンプレートのコメントのまま残し、何も書かない
- `published: false` で作る
- 週刊AWS の説明文を写さない。タイトルとリンク以外は自分の言葉で、サービスを使ったことがない人に向けて書く
- 記事は個人の学習記録。会社や業務を前提にした書き方をしない

### 2-3. 確かめる

```bash
npm run check -- --lint
npm run check
```

- `--lint` が NG なら、エラーの内容に従って直す
- `npm run check` で、作った下書きがすべて `drafts/<week>/` にあり「✍️ なし」になっていることを確かめる

### 2-4. 記録してコミットし、push する

```bash
echo "<week>" >> collected-weeks.txt
git add drafts/<week>/ collected-weeks.txt
git commit -m "collect: YYYY/M/D週の下書き（N 本）を作成"
node scripts/check-collect.js HEAD~1 HEAD
git push
```

`--dry-run` では、`collected-weeks.txt` の更新・コミット・push をしない。作った下書きは未コミットのまま残し、その旨を報告する。

## 3. 報告

最後に、次の形で短く報告する。ルーティンの実行ログとして aki が後から読むので、何が起きたかが一目でわかるようにする。

```
## aws-weekly の結果（<モード>）
- 確認: 新しい号あり（2026/10/5週） / 新しい号なし
- 収集: 下書き 15 本を drafts/2026-10-05/ に作成 / スキップ
  - aws-20261005-xxx: タイトル
  - …
- 注意: （あれば。チェックの NG、取得の失敗、作らなかったアップデートなど）
```

## うまくいかないとき

- **`fetch-weekly.js` が失敗する**（ネットワークの制限、ページの構造の変更など）: WebFetch で週刊AWS のページを読んで代わりにしてよい。ただし What's New のリンクは記事内では相対パス（`/about-aws/...`）なので、`https://aws.amazon.com` を付けた完全な URL にする。構造の変更でスクリプトが壊れていそうなら、そのことを報告に書く
- **push が権限で失敗する**: 無理に回避せず、何が失敗したかを報告して終了する
- 途中で失敗したときは、中途半端なコミットを push しない。どこまで終わったかを報告する
