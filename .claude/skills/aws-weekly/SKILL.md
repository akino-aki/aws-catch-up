# aws-weekly

週刊AWS を材料に Zenn 記事の下書きを作り、aki が勉強を書き足した記事を公開する。
運用の全体像は `docs/workflow.md`、記事の書き方は `CLAUDE.md` にある。このスキルはその手順を実行するためのもの。

## 引数

`$ARGUMENTS` を見て、モードを決める。

| 引数 | モード | やること |
|---|---|---|
| なし | 通常（ルーティン） | 確認 → 公開 → 収集 |
| `YYYY-MM-DD` | 週の指定 | その週の収集だけ（確認と公開はしない） |
| `--dry-run` を含む | お試し | 上のどちらかを、push・PR 作成・コミットをせずに行う |

週は「対象週の月曜日」の日付で表す（`週刊AWS – 2026/9/28週` なら `2026-09-28`）。

`--dry-run` は動作確認のためのモード。GitHub にも、aki の作業中のブランチにも何も残さないことが目的なので、ファイルを書き換える操作は「何が起きるはずか」の報告に置き換える。ただし収集の下書きは、中身を確認できるようにファイルとして作ってよい（コミットはしない）。

## 0. 準備

```bash
git fetch origin
git switch work
git pull --ff-only
```

`work` に未コミットの変更があるときは、aki の作業中のものかもしれないので、触らずに報告して終了する。

`npm install` / `npm ci` は不要。`scripts/` のスクリプトは Node.js の標準機能だけで動く（`zenn-cli` はプレビュー用で、この作業では使わない）。クラウドの環境ではパッケージの取得先への通信が許可されていないこともある。

## 1. 確認（通常モードのみ）

```bash
node scripts/fetch-weekly.js latest
```

出力の `week` について、`articles/aws-weekly-<week>.md` があるか確認する。

- **ある** → 新しい号はまだ出ていない。何もせず「新しい号なし」と報告して終了する（公開もしない）
- **ない** → 新しい号が出ている。2 に進む

週刊AWS は祝日の週に遅れたり、お休みの週があったりする。出ていない日は何もしないのが正しい動きなので、失敗扱いにしない。

## 2. 公開（通常モードのみ）

公開するかどうかは、自分で記事を読んで判断しない。スクリプトの判定に従う。判定を人間の目で確かめられるのはスクリプトの結果だけで、AI の判断が混ざると「なぜ公開されたのか」を後から追えなくなるため。

1. 公開対象の記事を公開用に書き換える

   ```bash
   npm run prepare-publish
   ```

   - 変更があれば `publish: <公開する週の一覧>を公開`（例: `publish: 2026/9/28週を公開`）でコミットし、`work` を push する
   - `--dry-run` では実行せず、代わりに `npm run check` の結果から「公開対象」の記事を報告する

2. `main` と `work` に差分があるか確認する

   ```bash
   git diff --quiet origin/main origin/work || echo "差分あり"
   ```

   差分がなければ公開するものはないので、3 に進む。

3. 公開用ブランチを作って PR を出す

   ```bash
   BRANCH="publish/$(TZ=Asia/Tokyo date +%F)"
   git switch -c "$BRANCH" work
   git push -u origin "$BRANCH"
   gh pr create --base main --head "$BRANCH" --title "publish: $(TZ=Asia/Tokyo date +%Y/%-m/%-d) の公開" --body "<npm run check の結果>"
   gh pr merge "$BRANCH" --auto --merge
   git switch work
   ```

   - 同じ名前のブランチがすでにあれば（同じ日に 2 回目の実行など）、末尾に `-2` などを付ける
   - 前回の公開用 PR が開いたまま残っていたら（チェックで止まったものなど）、新しい PR の本文にその PR を書いて、古い PR は「新しい PR で置き換えた」とコメントして閉じる。新しい PR のほうが `work` の最新の状態を含んでいるため
   - チェックが通れば自動でマージされる。結果を待つ必要はない。チェックが失敗しても、マージを強行したりチェックを回避したりしない。`main` のブランチ保護とチェックは、AI の間違いで未調査の記事が公開されるのを防ぐためのもの
   - `--dry-run` では、作るはずのブランチ名と PR のタイトル・本文を報告するだけにする

PR は `work` のコピー（`publish/...`）から出すので、このあと収集で `work` に push しても PR には入らない。

## 3. 収集

対象の週（通常モードは 1 で調べた `week`、週の指定モードは引数の週）の下書きを作る。

`articles/aws-weekly-<week>.md` がすでにあるときは作らない。aki の勉強が書かれているかもしれないので、上書きは絶対にしない。報告して終了する。

### 3-1. 材料を集める

```bash
node scripts/fetch-weekly.js week <week>
```

アップデートの一覧（タイトル・What's New の URL・週刊AWS の説明）が JSON で出てくる。

さらに、**アップデートごとに What's New のページ（`url`）を WebFetch で読み**、料金・対象リージョン・前提条件などの事実を確かめる。週刊AWS の説明は要約なので、細かい条件が抜けていることがある。件数が多いときは、並行して読んでよい。

### 3-2. 下書きを書く

`templates/weekly.md` をもとに、`CLAUDE.md` の「下書きの作り方」に従って書く。完成形の見本として、既存の記事（`articles/` の中でいちばん古いもの）を先に読んでおくと、表や注釈の使い方の粒度が合わせやすい。

特に間違えやすいところ:

- アップデートは元記事の日付順ではなく、`CLAUDE.md` のカテゴリ順に並べ替える。迷ったら「そのアップデートの目的」で分類する（例: Route 53 DNS Firewall はネットワークより「セキュリティ」）
- 「今週のアップデート一覧」の表には全件を載せる（行数がアップデートの件数と一致しないと CI で止まる）
- 「✍️ 自分の調査・勉強結果」は aki が書く欄。テンプレートのコメントのまま残し、何も書かない。ここに AI が何か書くと、調べていない記事が公開対象になってしまう
- `published: false` で作る
- 週刊AWS の説明文を写さない。タイトルとリンク以外は自分の言葉で、サービスを使ったことがない人に向けて書く

### 3-3. 確かめる

```bash
npm run check -- --lint
npm run check
```

- `--lint` が NG なら、エラーの内容に従って直す
- `npm run check` で、作った記事が「記入済み 0 / <件数>」「公開しない」になっていることを確かめる

### 3-4. コミットして push する

```bash
git add articles/aws-weekly-<week>.md
git commit -m "collect: YYYY/M/D週の下書きを作成"
node scripts/check-collect.js HEAD~1 HEAD
git push
```

`--dry-run` ではコミットも push もしない。作ったファイルは未コミットのまま残し、その旨を報告する。

## 4. 報告

最後に、次の形で短く報告する。ルーティンの実行ログとして aki が後から読むので、何が起きたかが一目でわかるようにする。

```
## aws-weekly の結果（<モード>）
- 確認: 新しい号あり（2026/10/5週） / 新しい号なし
- 公開: PR #3 を作成（2026/9/28週）、自動マージ予約済み / 公開対象なし / スキップ
- 収集: articles/aws-weekly-2026-10-05.md（17 件）を作成 / スキップ
- 注意: （あれば。チェックの NG、取得の失敗、残っている PR など）
```

## うまくいかないとき

- **`fetch-weekly.js` が失敗する**（ネットワークの制限、ページの構造の変更など）: WebFetch で週刊AWS のページを読んで代わりにしてよい。ただし What's New のリンクは記事内では相対パス（`/about-aws/...`）なので、`https://aws.amazon.com` を付けた完全な URL にする。構造の変更でスクリプトが壊れていそうなら、そのことを報告に書く
- **push や PR の作成が権限で失敗する**: 無理に回避せず、何が失敗したかを報告して終了する
- 途中で失敗したときは、中途半端なコミットを push しない。どこまで終わったかを報告する
