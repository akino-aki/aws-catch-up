## Amazon EC2 Future-dated Capacity Reservations が開始日の延期に対応

https://aws.amazon.com/about-aws/whats-new/2026/09/ec2-fcr-postpone-start-date/

### 🤖 AIの解説

| 項目 | 内容 |
|---|---|
| **要約** | 先の日付で予約したサーバーの枠を、あとから後ろにずらせるようになった |
| **料金** | 追加料金の記載なし |
| **対象** | Future-dated Capacity Reservations を使っている人 |

:::details そもそも Future-dated Capacity Reservations とは？
EC2（AWS の仮想サーバー）を「◯月◯日から、この台数ぶん必ず使える」ように、最大 120 日先まで前もって押さえておく予約の仕組みです。人気の店を予約しておくイメージで、大きなセールやイベントの日にサーバーが足りなくなるのを防げます。
:::

**今回なにが変わった？**

| | これまで | これから |
|---|---|---|
| 予定が延びたとき | キャンセルして予約し直す | 開始日だけ後ろにずらせる |
| 変更する前 | ― | 新しいコミット期間[^commit]の見積もりが表示される |

**どんなときにうれしい？**
新サービスのリリースやキャンペーンの日程が延びたとき。予約をキャンセルせずに、日付だけずらせます。

:::message
**確認ポイント**
EC2 コンソールの左メニュー →「キャパシティの予約（Capacity Reservations）」
キーワード: 将来の日付のキャパシティ予約、コミット期間
:::

## AWS Backup が Amazon FSx for NetApp ONTAP の論理的エアギャップボールトサポートを追加

https://aws.amazon.com/about-aws/whats-new/2026/09/aws-backup-air-gapped-vault-fsx-ontap/

### 🤖 AIの解説

| 項目 | 内容 |
|---|---|
| **要約** | 社内ファイルサーバーのバックアップを「誰も消せない金庫」に入れられるようになった |
| **料金** | AWS Backup の通常料金（詳細は料金ページ） |
| **対象** | 両方のサービスが使えるリージョン（東京・大阪を含む） |

:::details そもそも登場するサービスは何？
| サービス | ひとことで |
|---|---|
| AWS Backup | いろいろな AWS サービスのバックアップをまとめて管理するサービス |
| 論理的エアギャップボールト | バックアップを入れる「誰も書き換えたり消したりできない金庫」。ランサムウェア[^ransom]に本番環境を乗っ取られても、金庫の中は無事 |
| FSx for NetApp ONTAP | 企業でよく使われる NetApp 社のファイルサーバーを、AWS 上で使えるサービス |
:::

**今回なにが変わった？**

| | これまで | これから |
|---|---|---|
| FSx for ONTAP のバックアップ | 金庫には入れられなかった | 金庫に入れて保護できる |
| 他のアカウントとの共有 | ― | 金庫を別アカウントと共有し、そこから直接復元できる |

**どんなときにうれしい？**
社内のファイルサーバーを FSx for ONTAP に移している会社が、ランサムウェア対策や「バックアップを改ざんできないこと」を求める規制に対応したいとき。

:::message
**確認ポイント**
AWS Backup コンソール →「ボールト（Vaults）」
キーワード: logically air-gapped vault、Vault Lock、ランサムウェア対策
:::

**どんなときにうれしい？**
店舗や配送車の位置データを分析したいとき。これまでは緯度・経度を文字列などに変換して保存する手間がありましたが、そのまま保存できます。

:::message
**確認ポイント**

## Aurora PostgreSQL が Apache Iceberg および Parquet データのクエリに対応

https://aws.amazon.com/about-aws/whats-new/2026/09/aurora-postgresql-query-apache-iceberg-and-parquet/

### 🤖 AIの解説

| 項目 | 内容 |
|---|---|
| **要約** | S3 にある分析用のデータを、コピーせずに Aurora から SQL で直接読めるようになった |
| **料金** | 追加料金なし |
| **対象** | Aurora PostgreSQL 17.11 以降、18.6 以降（Serverless v2 を含む） |

:::details そもそも何の話？
Aurora PostgreSQL は、AWS が提供する PostgreSQL 互換の高性能なデータベースです。一方、分析用の大量のデータは、S3 に Iceberg や Parquet[^parquet] という形式で置かれていることが多く、データベースとは別の場所にあります。
:::

**今回なにが変わった？**

| | これまで | これから |
|---|---|---|
| S3 のデータを使いたいとき | ETL[^etl] で Aurora にコピーしてから使う | 外部テーブル（フォーリンテーブル）として登録すれば、そのまま SQL で読める |
| 裏側で動くもの | ― | DuckDB という分析が得意なエンジン |

**どんなときにうれしい？**
「アプリの DB にある顧客データ」と「S3 にある過去数年分のログ」を組み合わせて集計したいとき。データを移すための仕組みを作らずに済みます。

:::message
**確認ポイント**
対象バージョンかどうかを RDS コンソールで確認
キーワード: foreign table、DuckDB、データレイク
:::

### ✍️ 自分の調査・勉強結果

<!-- ここに自分で調べたこと・試したことを書く。調べなかった場合は「今週は未調査」 -->

[^parquet]: 分析に向いたファイル形式。列ごとにまとめて保存するので、特定の列だけを速く読めます。
[^etl]: Extract（取り出す）・Transform（加工する）・Load（入れる）の略。データをある場所から別の場所へ移す処理のこと。

## Amazon RDS が AMD ベースの M8a インスタンスをサポート

https://aws.amazon.com/about-aws/whats-new/2026/09/aurora-rds-amd-m8a/

### 🤖 AIの解説

| 項目 | 内容 |
|---|---|
| **要約** | 最新の AMD CPU を積んだサーバーで、データベースを動かせるようになった |
| **料金** | インスタンスの通常料金（詳細は RDS の料金ページ） |
| **対象** | RDS for PostgreSQL / MySQL / MariaDB。東京を含む 9 リージョン |

:::details そもそもインスタンスタイプの名前の読み方は？
RDS ではデータベースを動かすサーバーの性能を「インスタンスタイプ」で選びます。`M8a` は次のように読みます。

| 文字 | 意味 |
|---|---|
| M | CPU とメモリのバランスが取れた汎用タイプ |
| 8 | 世代（数字が大きいほど新しい） |
| a | AMD 製の CPU |
:::

**今回なにが変わった？**

| 項目 | M8a の特徴 |
|---|---|
| CPU | 第 5 世代 AMD EPYC |
| 仮想 CPU | 1 つが物理コア 1 つにそのまま対応。ほかの処理と CPU を取り合わない |
| 最大サイズ | 192 vCPU / メモリ 768 GiB |
| 通信速度 | ネットワーク最大 75 Gbps、ストレージ（EBS）最大 60 Gbps |

**どんなときにうれしい？**
データベースの性能を上げたい、または同じ性能をより安く手に入れたいとき。インスタンスタイプを変えるだけで試せます。

:::message
**確認ポイント**
RDS コンソールでデータベースを「変更」→「DB インスタンスクラス」
キーワード: インスタンスタイプの命名規則、Graviton・AMD・Intel の違い

## Amazon Aurora serverless がエージェント型 AI などのバースト性ワークロード向けにスケーリングを高速化

https://aws.amazon.com/about-aws/whats-new/2026/08/aurora-serverless-instant-16-acu-scaling/

### 🤖 AIの解説

| 項目 | 内容 |
|---|---|
| **要約** | 急にアクセスが増えたとき、1 秒以内に一気に性能を上げられるようになった |
| **料金** | これまでどおり、使った ACU の分だけ |
| **対象** | プラットフォームバージョン 3・4 は自動で有効 |

:::details そもそも Aurora Serverless とは？
アクセス量に合わせて、データベースの性能が自動で伸び縮みする Aurora です。性能の単位は **ACU**（Aurora Capacity Unit）で、使った ACU の分だけ料金がかかります。誰も使っていないときは 0 まで下げられます。
:::

**今回なにが変わった？**

| | これまで | これから |
|---|---|---|
| 急に負荷が増えたとき | 今の容量が小さいほど、少しずつしか増えない | 1 秒以内に最大 16 ACU を一気に追加できる |
| 0 に近い状態からの立ち上がり | 性能が追いつくまで時間がかかる | 大幅に短くなった |

**どんなときにうれしい？**
ふだんは静かで、ときどき急に大量の問い合わせが来るシステム。たとえば AI エージェントは、考えている間は静かで、動き出すと一気にデータベースへアクセスします。

:::message alert
プラットフォームバージョン 1・2 の場合は、バージョン 4 へのアップグレードが必要です
:::

:::message
**確認ポイント**
RDS コンソールでクラスターの「プラットフォームバージョン」を確認
キーワード: ACU、Aurora Serverless v2、プラットフォームバージョン
:::

## Amazon Aurora DSQL がパーシャルインデックスをサポート

https://aws.amazon.com/about-aws/whats-new/2026/10/aurora-dsql-partial-indexes/

### 🤖 AIの解説

| 項目 | 内容 |
|---|---|
| **要約** | 表の一部の行だけに、索引（インデックス）を作れるようになった |
| **料金** | 記載なし（索引が小さくなる分、保存コストは下がる） |
| **対象** | Aurora DSQL が使えるすべてのリージョン |

:::details そもそも Aurora DSQL とインデックスとは？
| 名前 | ひとことで |
|---|---|
| Aurora DSQL | サーバーの管理がいらず、複数のリージョンにまたがっても動く PostgreSQL 互換のデータベース |
| インデックス | 本の索引のように、検索を速くするための仕組み |
:::

**今回なにが変わった？**

| | これまで | これから |
|---|---|---|
| 索引の対象 | 表のすべての行 | `WHERE` で条件を付けて、一部の行だけにできる |
| 書き方 | `CREATE INDEX ASYNC ...` | `CREATE INDEX ASYNC ... WHERE 条件` |

**どんなときにうれしい？**
注文テーブルのように、「よく検索するのは処理中の注文だけで、何百万件もある完了済みの注文はほとんど見ない」場合。処理中の注文だけに索引を作れば、索引が小さく済み、検索も速くなります。

:::message
**確認ポイント**
PostgreSQL にも昔からある機能なので、PostgreSQL の公式ドキュメントでも仕組みを学べます
キーワード: partial index、CREATE INDEX ASYNC
:::

**どんなときにうれしい？**
