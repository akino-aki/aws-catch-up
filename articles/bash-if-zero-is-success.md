## 2-1 終了コードを見る

コマンドは、終わるときに**終了コード**という数字を返しますが、直前のコマンドの終了コードは`$?`で見れるそうです。

私の予想はこうでした。

|                      | 予想  |
| -------------------- | --- |
| あるファイルを`ls`したあとの`$?` | 0   |
| ないファイルを`ls`したあとの`$?` | 1   |
| 続けてもう一度`echo $?`     | 0   |

```bash
$ ls "my memo.txt"
'my memo.txt'
$ echo $?
0
$ ls nothing.txt
ls: cannot access 'nothing.txt': No such file or directory
$ echo $?
2
$ echo $?
0
```

2つめは1ではなく、**2**でした。

### 「失敗＝1」ではなく「失敗＝0以外」

bashのルールで決まっているのは「0なら成功、0以外なら失敗」ということだけで、0以外のどの数字を返すかは、コマンドごとに決まってました。

`ls`の場合は、`ls --help`に書いてありました。
これ～～～ちょっと引っ掛かった気持ちでした。笑
正常終了が0でそれ以外は1とかだろうな、と脳内的には予想できてたので普通に0以外の数字って言えばよかった。
1とか2とか明確に当てないと！って気持ちになってました。

```bash
$ ls --help | grep -A 3 "Exit status"
Exit status:
 0  if OK,
 1  if minor problems (e.g., cannot access subdirectory),
 2  if serious trouble (e.g., cannot access command-line argument).
```

マイナーか深刻かとは、どういう分け方か？
Claudeに聞いた。

| 数字  | 意味             | 例                                   |
| --- | -------------- | ----------------------------------- |
| 1   | マイナー（ちょっとした問題） | 指定したフォルダは見られたけど、その中のフォルダの一部が見られなかった |
| 2   | 深刻（大きな問題）      | 指定したもの自体が見られなかった                    |

`ls nothing.txt`は、「これを見せて」と頼んだもの自体がなかったので2になったということでした。

### 2回目の`echo $?`が0になる理由

3つめの予想は当たりました。
`echo $?`自体も1つのコマンドなので、「2を表示する」のに成功した`echo`の結果（0）で上書きされていました。
終了コードをあとで使いたいときは、すぐに`result=$?`のように変数に入れておくそうです。

### bashを起動した直後の`$?`は？

その理論でいくと、bashを起動した瞬間に`$?`したらどうなるんだろう？0かな？と気になったので、試してみました。

```bash
$ bash
$ echo $?
0
$ exit
```

0だろうなとは思ってましたが0でした！

本題と逸れますが、`bash`と打ったら、`clear`みたいに最初からになると思っていたけど、bashの中で、もう1つbashを起動している状態でした。
`exit`を入力すると、その子どものbashが終わって、親のbashに戻っていました。

毎回、PowerShellからGit Bashを起動しているのも同じで、入れ子になっています。

```
PowerShell
 └ bash（毎回最初に起動しているもの）
    └ bash（`bash`で起動したもの） ← exitでここが終わる
```

何段目にいるかは`echo $SHLVL`で分かるみたいです。
子どものbashは、親の変数をそのままでは受け継がないそうなので、試してみました。

```bash
$ x=hello
$ bash
$ echo "[$x]"
[]
$ exit
$ echo "[$x]"
[hello]
```

子どもの中では空っぽで、親に戻ると`hello`。
子どもに渡したいときは、`export x`のように`export`を使うらしい。

## 2-2 `grep`の終了コード

`grep`は、ファイルの中から文字を探すコマンド。
使えると便利だよ、と聞くけど正直使い方は覚えてなくてどうしても必要な時は都度調べてました。

改めて使い方↓
```
grep 探す文字 ファイル1 ファイル2 …
     └ 1つめ   └ 2つめ以降
```

終了コードは、「引数が成立しているなら、見つかっても見つからなくても0」と予想しました。

```bash
$ grep first "my memo.txt"
my first memo
$ echo $?
0
$ grep second "my memo.txt"
$ echo $?
1
$ grep first nothing.txt
grep: nothing.txt: No such file or directory
$ echo $?
2
```

| 結果 | 終了コード |
|---|---|
| 見つかった | 0 |
| 見つからなかった | 1（エラーではない） |
| ファイルがない | 2 |

見つからなかっただけなのに1。
Claudeに聞いたら、`grep`は「探す道具」であると同時に、「入っているか？」を判定する道具として作られているので、見つからなければ失敗（1）にしているそうです。

コマンドごとに終了コードが違うなら、全部0にはしないよね～そりゃそうだ。
終了コードも結局は、そのコマンドを作った人が「こういうときはこの数字」と決めた約束事だから、よく考えたらわかりそうなものなのですが。
予想しているときは、終了コードはコンピューターの仕組みで自然に決まるものだと思い込んでしまってました。

### `grep`でファイルを探すには？

`grep`って、特定のファイルがあるか探すのによく使われているイメージ。
だけどコマンドとしての機能は以下。
`grep`が探すのはいつも**ファイルの中身**で、ファイルそのものを探す機能はない。

| やりたいこと | コマンド |
|---|---|
| ファイルの中身に、ある文字が入っているか | `grep 文字 ファイル` |
| フォルダの中で、ある文字が入っているファイルを探す | `grep -rl 文字 フォルダ` |
| ファイルの名前で探す | `find フォルダ -name "名前"`、または`ls \| grep 名前` |

自分がよく見かけていたのは、`ls | grep 名前`のような形ですね。
`ls`が出したファイル名の一覧の中から探しているので、`grep`から見ると文字を探しているだけ・・・なるほどねえ。

## 2-3 `if`は0のときに`then`へ進む

いよいよ`if`です。

```bash
$ if ls "my memo.txt"; then echo "ある"; else echo "ない"; fi
$ if ls nothing.txt; then echo "ある"; else echo "ない"; fi
```

予想は、1つめが「ない」、2つめが「ある」。
正常なら0だから、`if`に当てはまらなくて「ない」に行くと思いました。

```bash
$ if ls "my memo.txt"; then echo "ある"; else echo "ない"; fi
'my memo.txt'
ある
$ if ls nothing.txt; then echo "ある"; else echo "ない"; fi
ls: cannot access 'nothing.txt': No such file or directory
ない
```

・・・あん、逆でした。

bashの`if`は**数字がtrueかfalseかを見ているのではなく、`if`のあとに書いたコマンドが成功したかを見ている**だけでした。
でもたしかに、普段ざっくりスクリプト読むときはちゃんと成功したら`then`以降の処理してるか？を確認してる。
なまじ勉強して知識が増えたせいで、考えすぎて間違えた。
何も知らないときに聞かれていたら、素直に答えられていたかも。

でも思い返すと、`then`のあとに書いてある処理の中身を見て「うまくいったときの処理っぽいから、ここに進むんだろう」と推測していただけな気もする。
仕組みが分かって読めていたわけではなかったですね。

|           | ほかの言語の`if`        | bashの`if`     |
| --------- | ----------------- | ------------- |
| 見ているもの    | 式の値（true / false） | コマンドの終了コード    |
| `then`に進む | 値がtrue（0以外）       | 終了コードが0（成功）   |
| `else`に進む | 値がfalse（0）        | 終了コードが0以外（失敗） |

なぜ成功が0なのかというと、成功のしかたは1通りだけど、失敗のしかたはたくさんあるから。0を成功にしておけば、0以外の数字で失敗の理由を区別できるからみたい。
bashのマニュアルにも、「成功を表す方法を1つにはっきり決めて、失敗をいろいろ表せるようにするため」と書いてありました。

https://www.gnu.org/software/bash/manual/html_node/Exit-Status.html

「`if`の条件式に当てはまったら0ってこと？」となりましたが、向きが逆で、`if`が0を作るのではなく、**コマンドが0を返したら`then`に進む**でした。
C言語では、「式が当てはまったら進む」と「成功したら0を返す」の両方を使っていたけど、bashの`if`が見るのは後者だけみたいです。

自分の中では、こう整理しました。

```
if コマンド; then 成功したらこれをする; else それ以外ならこれをする; fi
```

Claudeからは、「式」ではなく「コマンド」、そして`if`自体はコマンドではなく文法の決まり（キーワード）だと補足をもらいました。

もう1つ、予想していなかったのが、`ある`／`ない`の前に`ls`の出力も出ていたこと。`if`に入れたコマンドも、ふつうに実行されて、ふつうに表示されるそうです。
冒頭の`try()`関数で`>/dev/null 2>/tmp/err`を付けていたのは、これをその場で表示させないためでした（エラーは`/tmp/err`に取っておいて、NGのときに表示しています）。

# まとめ

- コマンドは終了コードを返す。0が成功、0以外が失敗。`$?`で直前の終了コードが見られる
- 0以外の数字の意味はコマンドごとに違う。`ls`の「ないファイル」は2、`grep`の「見つからない」は1
- `echo $?`自体もコマンドなので、2回続けると2回目は0になる
- `bash`と打つと、bashの中にもう1つbashが起動する。子どもは親の変数を受け継がない
- bashの`if`は式ではなく、コマンドの成功・失敗を見る。0（成功）なら`then`。ほかの言語と0の意味が逆に見える
