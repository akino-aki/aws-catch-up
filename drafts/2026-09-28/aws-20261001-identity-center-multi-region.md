# ✍️ 自分の調査・勉強結果

**マルチリージョンで何ができるのか**

Identity Center は、有効にするときに置き場所のリージョン（プライマリリージョン）を 1 つ選びます。ユーザー・グループ・許可セット・「誰がどのアカウントに入れるか」の割り当ては、すべてそのリージョンにあります。そのため、プライマリリージョンで障害が起きるとアクセスポータルに入れず、どのアカウントにもログインできなくなります。

マルチリージョンを有効にすると、これらが追加のリージョンへ自動でコピーされ、追加リージョンの入口からもアカウントに入れるようになります。ただし、入れるのは障害の前に設定済みだった権限だけで、設定の変更はプライマリリージョンでしかできません。

使うための条件は次のとおりです。

| 条件 | 内容 |
|---|---|
| インスタンスの種類 | 組織インスタンスだけ |
| ID ソース | Identity Center ディレクトリか外部 IdP。Active Directory では使えない |
| 暗号化キー | マルチリージョンのカスタマー管理 KMS キー |
| 外部 IdP の場合 | 複数の ACS URL[^acs] に対応している必要がある（Okta や Entra ID は対応、Google Workspace は未対応） |

**IAM との違い**

| | IAM | IAM Identity Center |
|---|---|---|
| 範囲 | 1 つのアカウントの中 | Organizations 配下の全アカウント |
| リージョン | グローバル | リージョナル |
| 認証情報 | 長期的（パスワード、アクセスキー） | 一時的（セッション時間で切れる） |

Identity Center でアカウントを割り当てると、各アカウントの中に `AWSReservedSSO_〜` という IAM ロールが自動で作られます。普段ログインしたときに右上に出ている名前が、このロールでした。Identity Center は「誰をどのアカウントのどのロールに入れるか」を管理する上の層で、アカウントの中で実際に権限をチェックしているのは IAM です。

**検証環境で試したこと**

検証に使ったアカウントはメンバーアカウントなので、Identity Center のコンソールを開くと「有効にする」の画面が出ました。組織の Identity Center（組織インスタンス）は管理アカウントにあるので、メンバーアカウントからは見えません。東京とバージニア北部で開いてみましたが、どちらも同じ画面です。

![東京リージョンの Identity Center](/images/aws-20261001-identity-center-multi-region/identity-center-tokyo.png)

![バージニア北部リージョンの Identity Center](/images/aws-20261001-identity-center-multi-region/identity-center-virginia.png)

試しに東京で「有効にする」を押すと、**アカウントインスタンス**を有効にする画面になりました。「組織の管理アカウントで設定することを勧める」という注意書きと、作成先のリージョンの確認が出ます。

![アカウントインスタンスを有効にする画面](/images/aws-20261001-identity-center-multi-region/identity-center-enable-account-instance.png)

作成後のダッシュボードでは、プライマリリージョンが `ap-northeast-1` になっていました。左のメニューにはユーザー・グループ・設定・アプリケーションの割り当てしかなく、AWS アカウントや許可セットの項目がありません。設定画面のタブにも、リージョンを追加する項目はありませんでした。

![アカウントインスタンスのダッシュボード](/images/aws-20261001-identity-center-multi-region/identity-center-account-instance-dashboard.png)

| | 組織インスタンス | アカウントインスタンス |
|---|---|---|
| 作れる場所 | 管理アカウント（または委任管理者） | 各アカウント |
| AWS アカウントへのログイン | できる | できない |
| AWS のアプリ（Amazon Q など）へのログイン | できる | 対応しているアプリだけ |
| マルチリージョン | できる | できない |

アカウントインスタンスは、組織の Identity Center がなくても、自分のアカウントで Identity Center が必要なアプリを試せるようにするためのものだと理解しました。今回の目的には合わないので、設定 →「管理」タブから削除しました。削除後には「東京リージョンの構成が削除された。このリージョンか他のリージョンで再度有効にできる」というメッセージが出て、リージョン単位のサービスであることがここからも分かりました。

**マルチリージョン KMS キーとは**

KMS の中に別の種類のキーがあるわけではなく、キーを作るときに「単一リージョンキー」か「マルチリージョンキー」かを選びます。作成後には変えられません。

![KMS のキー作成画面](/images/aws-20261001-identity-center-multi-region/kms-create-key-multi-region.png)

| | 単一リージョンキー（標準） | マルチリージョンキー |
|---|---|---|
| 置き場所 | 作ったリージョンだけ | プライマリ + 別リージョンのレプリカ |
| 鍵の素材とキー ID | そのリージョンだけのもの | プライマリとレプリカで同じ（ID は `mrk-` で始まる） |
| 料金 | 1 本あたり月 1 ドル程度 | プライマリもレプリカも 1 本ずつ数える |

作成画面でマルチリージョンを選んでも、リージョンを選ぶ画面は出ません。作るときはプライマリだけができ、レプリカは作成後のキーの詳細画面から追加します。レプリカはプライマリが止まっていても単独で使えて、プライマリに頼るのはローテーションとプライマリリージョンの変更だけです。

たとえば、AWS Backup で東京から大阪の DR 用リージョンにコピーする構成なら、東京と大阪で別々の KMS キーを使えば十分です。AWS Backup はコピーするときにコピー先のキーで暗号化し直すからです。マルチリージョンキーにしても、レプリカが 1 本として数えられるので料金は変わりません。

マルチリージョンキーが必要になるのは、**暗号化されたデータが、暗号化し直されないまま別のリージョンに届く**ときです。

| データを運ぶのは | キー |
|---|---|
| AWS のサービス（AWS Backup、S3 レプリケーション、RDS のリードレプリカなど） | 別々のキーで OK（コピー先で暗号化し直してくれる） |
| アプリや自分（アプリ側で暗号化したデータ、アクティブ-アクティブ構成、複数リージョンでの署名の検証など） | マルチリージョンキー |
| サービスが条件にしている（Identity Center のマルチリージョン） | マルチリージョンキー |

参考:
https://docs.aws.amazon.com/kms/latest/developerguide/multi-region-keys-overview.html

**あとでやること**

個人の AWS アカウントで組織インスタンスを作り、マルチリージョンを有効にする。ユーザーを作って、追加リージョンのアクセスポータルからもログインできるか確かめる。
