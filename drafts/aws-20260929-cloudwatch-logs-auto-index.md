:::details そもそも CloudWatch Logs Insights とは？
CloudWatch Logs は、アプリや AWS サービスのログを集めるサービスです。**Logs Insights** を使うと、SQL のようなクエリでログを検索できます。よく検索する項目（フィールド）にインデックスを付けておくと、検索が速く安くなります。
:::

# ✍️ 自分の調査・勉強結果

**フィールドインデックスのおさらい**

Logs Insights は、スキャンしたデータ量で料金が決まります。インデックスがないと、`requestId = "abc"` のような検索でも期間内のログを全部読んでから絞り込みます。フィールドインデックスは本の索引のようなもので、関係ないログを読み飛ばせるので、速く安くなります。

| 項目 | 内容 |
|---|---|
| 効く絞り込み | `=` と `IN`（完全一致）だけ |
| 対象のログ | JSON などの構造化ログと、AWS のサービスログ |
| 大文字・小文字 | 区別する |
| 対象になるログ | インデックスを作ったあとに届いたログだけ。各ログは届いてから 30 日間インデックスされる |

`@logStream` などのほか、CloudTrail の `eventName` や `eventSource` などは、AWS が最初からデフォルトのインデックスにしています。今回のアップデートは、それ以外で `=` / `IN` によく使われるフィールドを、AWS が自動でインデックスにしてくれるというものです。

**`filter` と `filterIndex` の違い**

| コマンド | 動き |
|---|---|
| `filter` | インデックスがあれば使い、なければ全部読む。結果は漏れない |
| `filterIndex` | インデックスされたログだけを探す。多くのロググループをまとめて検索するとき用 |

自動インデックスはクエリの傾向で入れ替わるので、ドキュメントでは `filter` を使うよう勧めています。`filterIndex` だと、インデックスされていなかった期間のログが結果から抜けてしまうからです。`filterIndex` で使いたいフィールドは、手動のインデックスポリシーに入れておく必要があります。

**検証環境で試したこと**

CloudWatch →「ログ」→「ログ管理」→ CloudTrail のロググループ →「フィールドインデックス」タブを開くと、`Default` と `aws_cloudtrail.management defaults` が Active になっていました。左のメニューは「ロググループ」ではなく「ログ管理」という名前になっています。また、Logs Insights を開くと、Logs Insights・Live Tail・Contributor Insights をまとめた新しい「Log Analytics」の画面になりました。

`eventName = "ConsoleLogin"` で 12 時間分を検索したところ、約 2,190 件（3.5 MB）のうち実際に読んだのは 5 件（9.8 KB）だけでした。実行前の「スキャンされた推定バイト数」も 9.8 KB で、実際と一致しています。

![インデックスで読み飛ばした件数が表示された結果](/images/aws-20260929-cloudwatch-logs-auto-index/cloudwatch-logs-insights-index-skip.png)

ただし、`eventName` は CloudTrail のデフォルトインデックスに入っているので、これは今回の自動インデックスの効果ではありません。インデックスがあるとどれだけ読み飛ばせるかは、よく分かりました。

**あとでやること**

デフォルトに入っていない `sourceIPAddress` などで何回か検索し、「フィールドインデックス」タブに自動で追加されるか、追加後に読み飛ばしが出るかを確かめる。
